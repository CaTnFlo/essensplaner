### Reproduce unnecessary planner relaxation

Run from the repository root:

```sh
node --input-type=module <<'NODE'
import assert from 'node:assert/strict';
import { readFileSync } from 'node:fs';
import { planeWoche, pruefePlan } from './js/planner.js';
const recipes = JSON.parse(readFileSync('data/recipes.json', 'utf8')).rezepte;
const state = { version: 1, aktuellerPlan: null, verlauf: [], favoriten: [], probiert: [], links: [] };
const result = planeWoche({ recipes, state, heute: new Date(2026, 10, 15), rng: () => 0.9 });
console.log(result.hinweise);
assert.ok(result.hinweise.some(h => h.includes('Fisch- oder Geflügel')));
const entry = id => ({ quelle: 'rezept', id, variante: null });
const feasible = { ...result.plan, neuSlot: 'A', slots: {
  A: entry('haehnchen-fajitas'), B: entry('lasagne'), C: entry('lachs-spinat-nudeln'),
} };
assert.deepEqual(pruefePlan({ plan: feasible, recipes, state }), []);
assert.equal(recipes.find(r => r.id === feasible.slots.A.id).typ, 'pool');
assert.equal(recipes.find(r => r.id === feasible.slots.B.id).typ, 'favorit');
assert.equal(recipes.find(r => r.id === feasible.slots.C.id).typ, 'favorit');
console.log('A feasible plan exists, including R2.');
NODE
```

The constant generator satisfies the documented `[0, 1)` interface. This is a deterministic counterexample, not an estimate of how often the production seeded generator hits this problem.

### Test gaps

- `tests/planner.test.mjs:520` says R4 is relaxed only when necessary, but tests a catalog containing no fish or poultry. It establishes the impossible case, not completeness when a valid combination exists.
- `tests/planner.test.mjs:237` checks the text of relaxation messages when rerolling, rather than proving no better stage was possible. The existing 500-seed cases provide useful coverage but do not prove exhaustive search.
- The baseline had no app or storage tests. Five new app tests cover URL sinks and save feedback. They execute actual app handlers with a minimal DOM stub; browser geometry, real Firestore behavior and iPhone gestures still require separate checks.

## Decisions still needed

1. Approve a complete planner search and separate subscription/save recovery before the UI implementation. For failed writes, recommended behavior is to keep an explicit unsaved draft with retry, rather than silently presenting it as persisted.
2. Clarify priority when every open link makes R4 impossible but a pool recipe would satisfy it. The current code chooses the link and relaxes R4. SPEC names both strict source priority and minimal rule relaxation without explicitly resolving this conflict. Keep the current priority until that decision is made.
3. Approve the separate [UI concept](ui-concept-2026-11-15.md). Its proposals do not change SPEC until implementation is approved.
